## 1 现状与问题

### 1.2 六个真问题（附证据）

| # | 问题 | 证据 |
|---|---|---|
| P-1 | **流程类规则不会被加载**。5 条 rules 的 frontmatter 只有 `description`，无一条 `alwaysApply: true`。`05-design-first` 这种"必须遵守的流程"靠关键词触发，用户说"加个功能"时大概率不命中 | `.codebuddy/rules/01..05` frontmatter |
| P-2 | **没有流水线载体**。`REQUIREMENTS.md` 是全项目需求总表、`P1-PLAN.md` 是一次性进度表（INDEX 已标为归档候选），不存在"单个需求从提出到交付"的统一状态文件 | `docs/INDEX.md` §11（P1-PLAN 归档候选） |

| P-4 | **测试有位置规范、无生成规范**。`TESTS.md` 只规定"测试放哪、怎么挂 `#[path]`"，没规定"AI 该生成哪些用例、覆盖底线是什么"；UI 层 4 个模块无测试，12 节只能靠人眼 | `docs/TESTS.md` §覆盖现状 |
| P-5 | **质量门禁未自动化**。`ACCEPTANCE.md` 是人工清单（12 节待验收），缺少"AI 交付前先自校验"的强制步骤 | `docs/ACCEPTANCE.md` |
| P-6 | **文档会漂移**。INDEX 已承认 2 处文档与代码不符（`index-panels-design.md` 承载位置过时、`tabs`/`tags` 无测试）→ 说明"照文档写"不可靠，必须强制**证据附代码行号** | `docs/INDEX.md` §10 |

### 1.3 根因

现有体系是**技术约束的集合**，不是**流程的骨架**。它回答了"代码怎么写"，没回答"一句话需求怎么变成一次交付"。

## 2 目标 / 非目标

### 目标

- G1：用户只提一句高层需求，AI 能自主走完 需求 → 设计 → 计划 → 实施 → 测试 → 质量 六个环节
- G2：每个环节有**可判定的准出条件**（Gate），AI 自己判不了的交回用户
- G3：全程产物落盘，AI 换会话/断上下文后能靠文件恢复进度
- G4：需求 ID → 设计章节 → 任务 → 测试 → 验收项 全程可追溯

### 非目标

- N1：**不做全自动无人值守**。涉及用户偏好、视觉/手感、方案选型的决策点一律交回用户（规则里明确列出交回清单）
- N2：不引入外部编排框架 / Agent 运行时。全部靠 `.codebuddy/rules` + `skills` + Markdown 状态文件实现
- N3：不改现有 5 条 rules 的技术内容，只调整加载方式与编号关系
- N4：不做 CI/CD。本项目是本地桌面应用，门禁是"AI 本地跑命令"，不是流水线

## 3 总体设计：Rules 与 Skills 的分工模型

### 3.1 一句话分工

> **Rules = 法律（不可协商，常驻上下文）；Skills = SOP（怎么做，按需加载）。**

| 维度 | Rules | Skills |
|---|---|---|
| 性质 | 硬约束，违反即错 | 流程能力，可裁剪但裁剪要记录 |
| 加载 | `alwaysApply` 或 glob 触发 | 按阶段关键词触发 |
| 粒度 | 短（单条约束 + 原因） | 长（分步骤 SOP + 模板 + 参考） |
| 回答的问题 | "什么不能做 / 必须留下什么" | "这件事按什么顺序做" |
| 变更频率 | 低（改一次影响全局） | 高（随实践迭代） |
| 失败代价 | 编译失败 / 数据损坏 | 效率低 / 漏步骤 |

### 3.2 协同的三个机制

**机制一：双向引用**

- Skill 的每个步骤末尾标注 `(rule: 04-notes-domain §2)`，让 SOP 自带约束跳转
- Rule 里声明"违反点由哪个 Skill 拦截"，例如 `07-quality-gates` 声明 G4 由 `implement-task` 执行

**机制二：状态文件（解决 AI 失忆）**

每个需求一个文件 `docs/exec-plans/<slug>.md`，是流水线唯一真值：

```markdown
## 状态机
需求 ✅ → 设计 ✅ → 计划 🔄(T3/T7) → 实施 ⬜ → 测试 ⬜ → 质量 ⬜

## 产物
| 环节 | 文件 | 门禁 |
|---|---|---|
| 需求 | docs/xxx-requirements.md | G1 ✅ |
| 设计 | docs/xxx-design.md | G2 ✅ |
| 计划 | 本文件 | G3 🔄 |

## 待用户拍板
- [ ] Q2：大库是否限制索引规模？
```

AI 每次开工先读它，不靠对话记忆。**这是把"AI 失忆"从概率问题变成工程问题的关键。**

**机制三：ID 贯通（证据链）**

```
R-3（需求） → 设计 §4.2（数据模型） → T-5（任务） → test_index_incremental（测试） → AC-7（验收）
```

每个下游产物必须引用上游 ID，缺链即门禁不通过。

### 3.3 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 把 6 环节全写成 1 个巨型 Skill | 上下文爆炸；本仓库 rules 全量已 ~500 行，再加 6 环节 SOP 会挤占代码上下文 |
| 全写成 alwaysApply 的 rules | 同上；且 SOP 类内容常驻会稀释注意力 |
| 引入外部 Agent 框架编排 | 违反 N2；本项目是单人本地项目，Markdown 状态文件足够 |
| 用 Git 分支/TODO 当状态载体 | 分支只能表达"在做"，表达不了"卡在哪个 Gate、等用户拍板什么" |

## 4 六环节详设

### 4.1 需求理解与澄清

**目标**：把"我想要个图谱视图"变成带编号、含非目标与边界的需求规格。

| 类型 | 名称 | 内容要点 |
|---|---|---|
| **Rule** | `08-artifacts.md` §1 | 需求文档强制章节：背景 / 目标 / **非目标** / 边界条件 / 验收标准；每条需求编号 `R-n`；**禁止捏造**，缺项写 `> 待补充` |
| **Rule** | `00-pipeline.md` §2 | 需求未澄清不得进入设计；G1 未过不得动 `src/` |
| **Skill** | `requirement-clarify` | 四步 SOP（见下） |

**Skill SOP（`requirement-clarify`）**：

1. **归类**：判断需求属于 新增功能 / 缺陷 / 重构 / 调研。缺陷与重构走简化流程（免设计文档，`05-design-first` §3）
2. **查证现状**：用 `search_content` / `read_file` 找到相关代码，**附 `文件:行号` 证据**，禁止写"应该是"
3. **生成假设清单**：对模糊点生成 3~7 条假设，每条标注「影响面 / 若不确认的默认取值」
4. **结构化提问**：一次性把问题打包成表格交给用户，**不问开放式问题**；同时给出 AI 的默认建议，用户可回"都按默认"

**边界条件识别清单**（Skill 内置固定项，逐条过）：空输入 / 超大输入 / 非法路径 / 并发写 / 外部程序改同一文件 / 应用崩溃 / 多库切换 / 隐藏文件与忽略目录 / 非 UTF-8。

**G1 门禁（机器可判）**：

- [ ] `docs/<slug>-requirements.md` 存在
- [ ] 含 目标 / 非目标 / 边界 / 验收标准 四节
- [ ] 每条需求有 `R-n` 编号
- [ ] 现状描述附 ≥1 处 `文件:行号`
- [ ] "待用户拍板"清单为空（或用户已明确回答）

### 4.2 方案设计

**目标**：产出含方案对比、数据模型、权衡说明、人工验收清单的设计文档。

| 类型 | 名称 | 内容要点 |
|---|---|---|
| **Rule** | `05-design-first.md`（已有） | 10 章模板，保留为设计文档的**章节规范** |
| **Rule** | `08-artifacts.md` §2 | 新增两条硬约束：① 方案对比**必须 ≥2 个**且写明否决理由；② 现状章节每条结论附代码证据 |
| **Skill** | `solution-design` | SOP + 决策记录（ADR）模板 |

**Skill SOP（`solution-design`）**：

1. **底盘核查**：先加载 `01-gpui-stack` / `02-architecture` / `04-notes-domain`，判断方案是否触碰铁律（依赖版本、分层方向、磁盘真值）
2. **框架能力核实**：涉及 GPUI 组件能力时**先查 <https://gpui-kit.com> 或源码**，不凭记忆猜 —— 这条来自 `05-design-first` §4 的血泪教训
3. **生成 ≥2 个方案**：维度 = 改动面 / 可测性 / 对用户数据的风险 / 后续扩展性
4. **权衡表**：明确"选了 A 就放弃了什么"
5. **数据模型与迁移**：持久化格式、旧数据兼容、索引可重建性
6. **产出人工验收清单**：只能靠人眼验的（滚动手感、着色、气泡位置）单独列出

**G2 门禁**：

- [ ] 10 章齐全（`05-design-first` §2 表格）
- [ ] 被否决方案 ≥1 个且附理由
- [ ] 现状章节每条结论附 `文件:行号`
- [ ] 测试计划写明"哪些能自动化 / 哪些要人工"
- [ ] 开放问题中**需用户拍板的已单独列出**
- [ ] **用户已确认**（人工门，AI 不得自行放行）

### 4.3 研发计划

**目标**：把设计拆成可独立验证、可排序的任务序列。

| 类型 | 名称 | 内容要点 |
|---|---|---|
| **Rule** | `00-pipeline.md` §4 | 任务粒度 ≤ 1 次提交；每个任务必须有「验收命令」；禁止跨阶段混合任务 |
| **Skill** | `exec-plan` | 拆解 SOP + `docs/exec-plans/<slug>.md` 模板 |

**Skill SOP（`exec-plan`）**：

1. **按设计文档的实施步骤分期**，每期产物可独立验证
2. **依赖排序**：标出前置任务，形成 DAG；无依赖的标为可并行
3. **优先级**：P0（不做则功能不成立）/ P1（体验）/ P2（锦上添花）
4. **工作量估算不用人天**，用「改动文件数 + 是否需新建模块 + 是否需人工验收」三档：S / M / L
5. **每任务写清**：涉及文件、验收命令、关联 `R-n`、是否需人工验收

**G3 门禁**：

- [ ] 每个任务有唯一 `T-n` 编号、依赖、验收命令
- [ ] 每个任务能独立编译通过（不存在"全做完才能编"的任务）
- [ ] 每个 P0 任务都关联 ≥1 条 `R-n`
- [ ] 计划文件已落盘到 `docs/exec-plans/<slug>.md`

### 4.4 实施研发

**目标**：按计划编码，遵守全部技术铁律，提交前自校验。

| 类型 | 名称 | 内容要点 |
|---|---|---|
| **Rule** | `01` / `02` / `03` / `04`（已有） | 依赖铁律、分层单向、Rust 规范、领域规则 |
| **Rule** | `06-git-workflow.md`【新增】 | 提交粒度 = 1 个任务；commit 格式沿用 Conventional Commits；**禁止顺手改动无关代码** |
| **Rule** | `07-quality-gates.md`【新增】 | G4 提交前必跑的 4 条命令 |
| **Skill** | `implement-task` | 编码 SOP + 提交前自校验 |
| **Skill** | `gpui-desktop-dev` / `notes-app-dev`（已有） | 降为**技术底座**，由 `implement-task` 按需调用 |

**Skill SOP（`implement-task`）**：

1. **读状态文件**确认当前任务与前置完成情况
2. **加载对应技术底座 skill**（涉及 GPUI 组件 → `gpui-desktop-dev`；涉及 Vault/索引/写盘 → `notes-app-dev`）
3. **改前先跑一次编译**，确认起点是绿的（GPUI 编译慢，避免把时间浪费在排查历史错误）
4. **编码**，遵守 `03-rust-code-style`；`core/` 逻辑必须可单测（`02-architecture` §2 判据）
5. **自校验四连**（G4）：

```bash
cargo build 2>&1 | grep -i warning   # 必须为 0
cargo clippy --all-targets           # 必须干净
cargo fmt --check                    # 必须无 diff
cargo test                           # 必须全绿
```

6. **范围自检**：`git diff --stat` 与计划的"涉及文件"比对，超出须说明原因
7. **回写状态文件**：任务置 ✅，记下实际改动与偏差

**G4 门禁**：上述 4 条命令全绿 + 变更范围与计划一致 + 新增 `core/` 逻辑有 `#[test]`。

### 4.5 测试验证

**目标**：自动生成并执行用例，覆盖功能、边界、回归。

| 类型 | 名称 | 内容要点 |
|---|---|---|
| **Rule** | `09-testing-standard.md`【新增】 | ① 沿用 `docs/TESTS.md` 的 `#[path]` 挂载约定；② 覆盖底线；③ 三类"测不了"的处理原则 |
| **Skill** | `test-verify` | 用例生成 SOP + 执行与回归 |

**覆盖底线（Rule 09 核心内容）**：

| 层 | 底线 |
|---|---|
| `core/` 新增模块 | 必须有对应 `tests/<层>/<模块>.rs` 并 `#[path]` 挂载 |
| `core/` 新增 pub 函数 | 正常路径 + 至少 1 个边界（空 / 非法 / 超大） |
| 涉及文件系统的 | 必须 `tempfile`，**绝不污染真实用户目录**（`03-rust-code-style` §6） |
| 涉及写盘的 | 必须有"写失败"路径的用例 |
| `ui/` | 只测两类：查表类静态数据、纯函数与纯状态迁移（`TESTS.md` 已有结论） |

**Skill SOP（`test-verify`）**：

1. **从需求与设计抽用例**：每条 `R-n` → 至少 1 个用例；设计文档"异常与边界"章节 → 逐条对应用例或人工项
2. **边界清单**（固定九项，逐条判"能自动化 / 要人工 / 不适用"）：空输入、超大输入、非法路径、并发写、外部程序改文件、崩溃后半截文件、多库切换、隐藏/忽略文件、非 UTF-8
3. **处理"测不了"的三原则**（延续 `TESTS.md` 已有实践）：
   - 写真实 `app_data_dir()` / 发真实 HTTP 的 → **抽出纯规则函数测**，函数本身留人工
   - 状态迁移在 `cx.listener` 闭包里的 → **仅当出过 bug 才为可测性重构**
   - 渲染 / 手感 / 着色 → **不硬凑测试**，登记到 `ACCEPTANCE.md`
4. **执行与回归**：`cargo test` 全绿；若修改了既有行为，必须在设计文档注明"行为变更"并检查受影响的旧测试

**G5 门禁**：

- [ ] 新增/修改的 `core/` 模块已挂载测试
- [ ] 边界清单九项逐条有归属（测试 / 人工 / 不适用并注明）
- [ ] `cargo test` 全绿
- [ ] 无新增测试污染真实用户目录（检查是否有硬编码 `app_data_dir()`）

### 4.6 质量保障与品质保障

**目标**：交付前自审 + 静态检查 + 缺陷追踪 + 验收标准闭环。

| 类型 | 名称 | 内容要点 |
|---|---|---|
| **Rule** | `07-quality-gates.md`【新增】 | 质量门禁总表 G1–G6，声明"谁执行、谁拍板" |
| **Rule** | `10-acceptance.md`【新增】 | 人工验收的唯一去处是 `docs/ACCEPTANCE.md`，**禁止再散落到各设计文档** |
| **Rule** | `08-artifacts.md` §4 | 交付后必须回写 `docs/INDEX.md`（状态 + 对应模块 + 缺口） |
| **Skill** | `quality-review` | 自审 SOP + 缺陷追踪 + 验收交付 |

**Skill SOP（`quality-review`）**：

1. **代码自审清单**（对照 `03-rust-code-style` 逐条）：
   - `core/` 无 `unwrap()` / `expect()`（测试除外）
   - `core/` 无 gpui 组件类型、无布局样式
   - 错误类型分层正确（`core/` 用 `thiserror`，`ui/` 用 `anyhow` + `context`）
   - 公共 API 有 `///`，注释解释"为什么"而非复述代码
   - `render()` 内无 IO / 重计算
2. **静态检查**：`cargo clippy --all-targets` + `cargo fmt --check`；确需 `#[allow]` 的必须写明原因
3. **缺陷分级与追踪**：

| 级别 | 定义 | 处理 |
|---|---|---|
| **Blocker** | 丢数据、崩溃、编译不过 | 当次必须修，不得交付 |
| **Major** | 功能不符需求、明显性能问题 | 记入计划作新任务，可下轮修 |
| **Minor** | 体验瑕疵、命名、文档漂移 | 记入 `docs/INDEX.md` §10 已知缺口 |
| **Won't fix** | 明确不做的 | 写进设计文档"非目标" |

4. **验收交付**：把只能人眼验的项追加到 `docs/ACCEPTANCE.md`，**格式可逐条打勾**，并明确告诉用户"这些需要你亲自看"
5. **回写索引**：更新 `docs/INDEX.md`（新增文档登记行、状态 ✅/⚠️、对应模块、缺口登记）

**G6 门禁**：

- [ ] 自审清单全过
- [ ] clippy / fmt 干净
- [ ] 无 Blocker 级缺陷遗留
- [ ] 人工验收项已登记进 `ACCEPTANCE.md` 并交付用户
- [ ] `docs/INDEX.md` 已回写
- [ ] 状态文件 `docs/exec-plans/<slug>.md` 六环节全 ✅

## 5 编排机制

### 5.1 元技能 `rd-orchestrator`

用户"只提需求"的入口。它不写代码，只做三件事：

1. **定位阶段**：读 `docs/exec-plans/<slug>.md`（不存在则判定为需求阶段，新建）
2. **派发**：按阶段加载对应 Skill
3. **守门**：每个环节结束跑对应 Gate；机器项自检，人工项产出"待拍板清单"交回用户

### 5.2 阶段判定表

| 状态文件 | 用户说的是 | 进入 |
|---|---|---|
| 不存在 | 任意需求 | 需求澄清 |
| 存在，需求 ✅ 设计 ⬜ | 继续 / 默认 | 方案设计 |
| 存在，设计 ✅ | 开始做 / 实施 | 研发计划 → 实施 |
| 任意阶段 | "修个 bug，现象明确" | **跳过 G1/G2**，直达实施（`05-design-first` §3） |
| 存在，全部 ✅ | 新需求 | 新建状态文件 |

### 5.3 必须交回用户的决策点（规则强制）

以下情况 AI **不得自行推进**，必须生成"待拍板清单"：

1. 方案选型有 ≥2 个代价相当的候选
2. 改动涉及用户数据格式（持久化格式、迁移）
3. 需求存在无法从代码推断的产品偏好（默认行为、交互形态）
4. 需要人眼验收（视觉 / 手感 / 性能体感）
5. 超出计划范围的改动（`06-git-workflow` 最小变更原则）
