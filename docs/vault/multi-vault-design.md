# 多 Vault 管理 — 设计文档

> 状态：**已确认**（2026-09-28）· 开放问题全部采纳推荐方案（见 §11）· 可进入 S1 开发
> 目标：实现类似 Obsidian 的 vaults 机制——库可注册、可切换、启动校验、持久化恢复
> 关联：`docs/DESIGN.md`、`docs/REQUIREMENTS.md`、`.codebuddy/rules/04-notes-domain.md`
> 本文所有"现状"结论均来自源码核实，附 `文件:行号`

---

## 1. 现状与问题

当前是**单库**模型，"库"甚至不是一个全局概念：

| 现状 | 证据 |
|---|---|
| `Vault` 只有 `root` 一个字段，无 id / 名称 / 元数据 | `src/core/vault.rs:21-23` |
| 库被 `FilesPanel` 私有持有，**不在 `AppState`** | `src/ui/file_tree.rs:31` |
| 持久化是单值：`vault.json` 只有 `root`，覆盖式写入 | `src/state/workspace.rs:45-48,50-57` |
| 切换库时对已打开标签**零处理**，`open_notes.json` 会混入跨库路径 | `src/ui/file_tree.rs:83-120`（`open_folder`） |
| "最近打开"是全局列表，不按库过滤 | `src/ui/file_tree.rs:39,378-388`；`workspace.rs:164-177` |
| watcher 靠"覆盖字段即 drop"重建，无显式停止 | `src/core/watcher.rs:33-97`；`file_tree.rs:391-419` |
| **标签恢复早于库恢复**：`restore_open_notes` 在 `Workspace::new`，库恢复在 `FilesPanel` 首帧 | `src/app.rs:299` vs `src/ui/file_tree.rs:612-615` |
| `state/workspace.rs` **没有测试**（库路径、标签、最近文件的读写全无覆盖） | `src/state/` 下只有 `single_instance/tests.rs` |

因此"多 Vault"不是加个下拉框，而是要补上：**库身份 + 注册表 + 全局持有 + 切换时的状态迁移 + 启动校验**。

## 2. 目标 / 非目标

**目标**

| # | 目标 |
|---|---|
| G1 | 注册多个库（名称 + 路径），可切换 |
| G2 | 目录树左下角提供库选择器，含"添加库"入口 |
| G3 | 启动时校验所有已注册库，有问题给出明确提示与处理 |
| G4 | 持久化库列表与当前库，重启后恢复 |
| G5 | 与现有打开/编辑/保存/监听流程无缝衔接，异常可理解 |

**非目标**

- 跨库搜索、跨库双链 —— **已决定不做**（2026-10-20）：搜索与双链只覆盖**当前库**，
  切库即切换检索范围。各库的索引独立构建，不做合并，也不引入"跨库"这一层概念
- 库级独立配置（沿用全局 `AppConfig`；库级配置留作后续）
- 同时监听多个库（只监听当前库）
- 云端同步、库加密、库模板

## 3. 方案概述

### 3.1 三个可选放置位置（含否决理由）

| 方案 | 内容 | 结论 |
|---|---|---|
| A. 库列表放 `config.json` | 作为 `AppConfig` 的一类配置 | ❌ 否决：配置是**偏好**且支持导入导出，库列表是**工作区状态**；导出配置会把本机路径带出去 |
| B. 新增 `vaults.json`（`state/workspace.rs`） | 与 `layout.json` / `open_notes.json` 同类 | ✅ **推荐** |
| C. 复用并扩展 `vault.json` | 单值改数组 | ❌ 否决：文件名与语义都不再匹配，不如新文件 + 显式迁移 |

### 3.2 推荐的总体结构

```
state/workspace.rs
   vaults.json ──► VaultRegistry { vaults: [ {id,name,path} ], active: Option<id> }
                        │
                        │ 启动时 load + 校验（§4）
                        ▼
AppState（app.rs）持有 registry 与 active_root
   ├─ FilesPanel       首帧按 active_root 恢复树 + 启 watcher
   ├─ restore_open_notes  按 active_root 过滤后再恢复标签
   └─ 退出 / 切换时      写回 vaults.json
```

关键调整：**把"当前库"从 `FilesPanel` 提到 `AppState`**，并让"确定 active 库"发生在"恢复标签"之前。

## 4. 数据模型与持久化

### 4.1 结构

```rust
/// 一个已注册的库
pub struct VaultEntry {
    /// 稳定 id：新增时生成（路径可改，id 不变）
    pub id: String,
    /// 显示名：新增时默认取目录名，可改
    pub name: String,
    pub path: PathBuf,
}

/// 库注册表（vaults.json）
#[derive(Default, Serialize, Deserialize)]
#[serde(default)]
pub struct VaultRegistry {
    pub vaults: Vec<VaultEntry>,
    /// 当前库 id；为 None 表示未选择任何库
    pub active: Option<String>,
}
```

### 4.2 文件与读写

| 项 | 值 |
|---|---|
| 路径 | `~/Library/Application Support/xink/vaults.json`（`app_data_dir()/vaults.json`） |
| 格式 | `serde_json::to_string_pretty`（沿用 `workspace::write_json`） |
| 写入时机 | 新增库、移除库、重命名、切换库、退出应用 |
| 读取时机 | 启动时（`Workspace::new` 内 `AppState` 初始化时） |
| 容错 | 文件缺失 / JSON 损坏 → `VaultRegistry::default()`（空列表），**不阻塞启动** |

### 4.3 旧数据迁移

首次读到 `vaults.json` 不存在、但旧的 `vault.json` 存在时：

1. 读 `vault.json` 的 `root`；
2. 若 `root.is_dir()` → 生成一条 `VaultEntry`（id 新建，name 取目录名），并设为 active；
3. 写入 `vaults.json`，**保留 `vault.json` 不删**（避免回滚时丢数据，后续版本再清理）。

> `load_vault()` 目前失效时静默返回 `None`（`workspace.rs:60-67`），迁移逻辑同样不得阻塞启动。

### 4.4 需确认

- **D1**：`id` 用 UUID 还是路径的稳定哈希？推荐 UUID（路径变更后 id 不变，便于将来挂库级状态）。
- **D2**：是否允许重命名后路径保持不变但名称重复？推荐允许（显示时附带路径区分）。

## 5. 启动校验（G3）

### 5.1 校验项

| 检查 | 判定 | 处理 |
|---|---|---|
| 路径存在 | `path.exists()` | 否则标记 `Missing` |
| 是目录 | `path.is_dir()` | 否则标记 `NotDir` |
| 可读 | 试探 `fs::read_dir(path)` | 否则标记 `NoPermission` |
| 重复 | `canonicalize` 后与其它条目相同 | 标记 `Duplicate`（**对称判定**：两条都会标上；"保留先注册的那条"由上层按注册顺序决定） |
| 嵌套 | A 是 B 的祖先目录 | 标记 `Nested`（**警告，不禁止**） |

```rust
pub enum VaultStatus {
    Ok,
    Missing,       // 路径不存在（移动/删除/未挂载的盘）
    NotDir,        // 路径是文件
    NoPermission,  // 无读权限
    Duplicate,     // 与其它库路径重复
    Nested,        // 被其它库包含（警告）
}
```

### 5.2 启动流程（推荐放在 `Workspace::new`，早于标签恢复）

```
load_vaults()（含 vault.json 迁移）
   → 逐项校验 → Vec<(VaultEntry, VaultStatus)>
   → 解析 active：
        active 存在且有效  → 用它
        active 缺失/失效   → 回落第一个 Ok 的库，并记一条提示
        没有任何 Ok 的库   → active = None（空库状态，提示"打开文件夹作为库"）
   → AppState { registry, active_root }
   → restore_open_notes（按 active_root 过滤）
   → FilesPanel 首帧恢复树 + watcher（不再自己读 vault.json）
```

### 5.3 反馈方式

| 情况 | 反馈 |
|---|---|
| 全部有效 | 静默 |
| 部分失效 | 目录树底部状态条：`⚠ 2 个库路径失效` + 提供「重新定位 / 移除」入口 |
| 当前库失效已回落 | 状态条提示：`原库「xxx」已失效，已切换到「yyy」` |
| 无任何有效库 | 空态：提示"打开文件夹作为库"（现有空态文案复用） |
| `vaults.json` 损坏 | 打印日志 + 空列表启动（与 `AppConfig::load` 的容错策略一致） |

原则：**校验失败绝不阻塞启动**，与现有 `AppConfig::load`、`load_open_notes` 的容错风格一致。

## 6. 交互设计（G1 / G2）

### 6.1 库选择器（目录树左下角）

```
┌────────────────────────────┐
│ [ 我的笔记            ⌄ ]  │  ← 当前库名 + 下拉箭头
├────────────────────────────┤
│ 目录树 …                    │
```

点击展开菜单：

| 项 | 行为 |
|---|---|
| 库列表（当前项带 ✓） | 切换 |
| 打开文件夹作为库… | 新增（§6.2） |
| 管理库… | 重命名 / 重新定位 / 移除（本期可选，见 D4） |

### 6.2 新增库

1. 选择器 → 「打开文件夹作为库…」→ 系统目录选择（复用现有 `prompt_for_paths`，`file_tree.rs:84-89`）
2. 弹出命名输入：默认取目录名，可改
3. 校验：
   - 路径无效 / 不是目录 → 提示"选择的路径不是有效目录"，终止
   - 与已有库重复 → 提示"该目录已是库「xxx」"并询问是否直接切换过去
   - 被已有库包含 → **警告但允许**（告知"该目录位于库「xxx」内，笔记会被重复计入"）
4. 写入 `vaults.json` → 询问是否立即切换（推荐：默认切换，与 Obsidian 一致）

### 6.3 切换库

切换涉及状态迁移，顺序必须是：

1. 若当前有**未保存改动** → 先提示保存/放弃（复用现有 `dirty` 与保存逻辑，见 `04-notes-domain.md` §3/§4）
2. 关闭所有**不属于新库**的标签（调用 `OpenTabs::remove`，`tabs.rs:73`），并重写 `open_notes.json`
3. `active = 新库 id`，写 `vaults.json`
4. `FilesPanel` 重载目录树（`refresh`）、**重启 watcher**（先停后启）
5. 刷新"最近打开"（按新库过滤）
6. 状态条提示 `已切换到「xxx」`

### 6.4 配置管理界面（独立窗口）

左下角菜单底部提供「配置管理…」，打开一个**独立窗口**做完整的增删改查。
与库选择器的分工：选择器负责"切换当前库"，管理界面负责"维护库列表本身"。

| 项 | 设计 |
|---|---|
| 形态 | 独立窗口；**单例**（重复点击聚焦已有窗口，沿用设置窗口的做法） |
| 列表 | 每行展示：名称（可编辑）、路径、状态（可用 / 失效原因）、当前库标记 |
| 新建 | 选择目录 + 填写名称；已注册的路径提示"已是库"并转为切换 |
| 重命名 | 直接编辑名称，失焦或回车即保存 |
| 重新定位 | 目录失效时选择新路径；**id 不变**（挂在该库上的状态不丢） |
| 删除 | 从注册表移除，需二次确认；**绝不删磁盘文件**，确认框里写明 |
| 设为当前 | 切换后立即生效（文件树由 `applied_vault_root` 守卫重载） |

交互与反馈：

- 所有操作**即时落盘**（`save_vaults`）并 `refresh_windows()`，无需"保存"按钮；
- 删除是破坏性操作，采用确认对话框（沿用设置的 `AlertDialog` 风格）并说明"仅移除记录，磁盘文件保留"；
- 失效路径在列表中显式标出原因（路径不存在 / 不是目录 / 无权限），并提供「重新定位」入口；
- 全部库被删除后回到空态，提示"打开文件夹作为库"。

### 6.5 与现有入口的关系

| 现有入口 | 新语义 |
|---|---|
| `Cmd+O` / 「打开库」按钮 | 选择目录 → 若已注册则切换，否则新增并切换（§6.2） |
| 「最近打开」列表 | 按当前库根过滤后展示（§7） |
| 空态提示 | 无库时提示添加库 |

## 7. 与现有文档管理流程的集成

| 模块 | 现有行为 | 多库改造 |
|---|---|---|
| **标签 `open_notes.json`** | 全局路径列表，混入跨库路径 | 保存/恢复时**按 active 库根过滤**；切换库时重写（只保留属于新库的标签） |
| **最近文件 `recent.json`** | 全局，最多 10 条 | 仍全量存（保留历史成本最低），**展示时按当前库过滤**，取前 5 条 |
| **watcher** | 覆盖字段即 drop 重建 | 新增显式 `stop_watcher()`；切换时先停再启；**只监听当前库** |
| **退出持久化** | 只存布局 + 标签（`app.rs:318-331`） | 增加：写 `vaults.json`（active 已在切换时写入，退出再兜一次） |
| **`FilesPanel` 多实例** | 布局恢复可能创建多个实例，各自持有 vault/watcher | 库状态提到 `AppState`，面板只读，避免多实例不一致 |
| **启动顺序** | 标签恢复早于库恢复 | 调整为：先定 active 库 → 再恢复标签（§5.2） |

## 8. 异常与边界（逐场景）

| # | 场景 | 反馈 | 处理 |
|---|---|---|---|
| E1 | 新增时选到文件 | "选择的路径不是目录" | 终止，不写入 |
| E2 | 新增时路径无权限 | "无法读取该目录（权限不足）" | 终止 |

| E5 | 库名重复 | 允许（列表显示时用路径辅助区分） | — |
| E6 | 库名为空 | 回落到目录名 | — |
| E7 | 启动时库路径失效 | 状态条 `⚠ N 个库路径失效` | 提供重新定位 / 移除 |

| E11 | `vaults.json` 损坏 | 日志 + 空列表 | 不阻塞启动 |
| E12 | 库目录被外部删除（运行中） | watcher 事件 → 状态条提示 | 提供重新定位 / 移除 |

## 10. 人工验收清单

1. 启动时若上次库有效 → 自动恢复，树与监听正常
2. 左下角选择器显示当前库名，点击可看到全部已注册库
3. 切换到另一个库 → 目录树换成新库内容，标签只保留属于新库的
4. 切换时有未保存改动 → 先提示保存，取消则不切换
5. 「打开文件夹作为库…」新增后出现于列表并可切换
6. 新增已存在的目录 → 提示"已是库"并可直接切换
7. 新增子目录 → 给出嵌套警告
8. 手动删除某库目录后重启 → 状态条提示失效，提供重新定位/移除，应用仍可启动
9. 所有库都失效 → 空态提示，不崩溃
10. 退出再启动 → 库列表与当前选择正确恢复
11. 旧版本升级（`vault.json` 存在）→ 自动迁移为一条库记录
12. 切换后 watcher 只监听新库（在新库建文件有反应，在旧库建文件无反应）

## 11. 决策记录（2026-09-28 确认，全部采纳推荐方案）

| # | 问题 | **决策** | 说明 |
|---|---|---|---|
| **D1** | id 用 UUID 还是路径哈希 | **UUID** | 路径变更后库身份保留；因不引入 uuid 依赖，用时间戳+路径派生的稳定字符串 |
| **D2** | 是否允许嵌套库 | **允许 + 警告** | 新增/校验时提示"位于库「xxx」内，笔记会被重复计入"，不禁止 |
| **D3** | 切换库时旧库标签怎么处理 | **关闭**不属于新库的标签 | 切换时先提示保存未保存改动，再关闭并重写 `open_notes.json` |
| **D4** | 本期是否做"管理库" | **先做移除 + 重新定位**，重命名延后 | 重命名属 S4 可选 |
| **D5** | 最近文件是否按库过滤显示 | **全量存，按当前库过滤显示** | 保留历史成本最低，兼容既有 `recent.json` |
| **D6** | 库列表存储位置 | **`vaults.json`（`state/workspace.rs`）** | 与 `layout.json`/`open_notes.json` 同类；不放 `config.json`（配置可导出，会带出本机路径） |
| **D7** | 是否支持库级配置 | **非目标** | 沿用全局 `AppConfig`，后续再议 |

主要风险：

- **启动顺序调整**是本改动中最容易出错的部分（标签恢复要挪到库确定之后），需重点验证；
- `FilesPanel` 可能有多个实例，库状态必须提到 `AppState` 才不会不一致；
- watcher 若未正确停止，会出现"旧库仍在监听"的隐蔽问题（验收第 12 条覆盖）。

## 12. 实施步骤（每期可独立验证）

| 阶段 | 内容 | 产出 |
|---|---|---|
| **S1 数据层** | `VaultEntry` / `VaultRegistry` / 校验函数 / `vaults.json` 读写 / `vault.json` 迁移；新增 `state/workspace/tests.rs` | 可单测，不动 UI |
| **S2 启动链路** | `AppState` 持有 registry 与 active_root；启动校验与回落；标签恢复按库过滤 | 启动行为正确 |

## 14. 后续优化（2026-09-28 提出，方案待确认）

### 14.1 切换库后清理"最近访问"

**问题**：`FilesPanel.recent` 在 `FilesPanel::new` 时一次性 `load_recent_notes()`（`file_tree.rs:59`），
渲染 `render_recent`（`take(5)`）**不按当前库过滤**；切换库时没有任何处理（`file_tree.rs` 的切换守卫只管树与监听）。
于是切到新库后，底部仍显示上一个库的笔记，点击可直接打开库外文件。

**方案**（与 D5"全量存、按库显示"一致）：

| 项 | 设计 |
|---|---|
| 数据来源 | 仍是全局 `recent.json`（保留跨库历史，成本最低） |
| 触发时机 | 切换库的守卫里（`applied_vault_root` 变化时）重新 `load_recent_notes()` |
| 过滤逻辑 | `render_recent` 只保留 `path.starts_with(当前库根)` 的前 5 条 |
| UI 刷新 | 守卫里更新内存 `recent` 后 `cx.notify()` |
| 空态 | 过滤后为空则不渲染该区块（或显示"本库还没有最近访问"） |

要点：过滤放在**显示层**而不是写入层——写入层过滤会丢掉其它库的历史记录。

### 14.2 库管理窗口尺寸紧凑化

**问题**：`open_vault_manager` 用 `WindowOptions::default()`（`vault_manager.rs`），框架默认尺寸偏大。

**方案**：复用设置窗口 §7.1 的自适应做法：

| 项 | 值 |
|---|---|
| 宽度 | 固定 ~560px |
| 高度 | 顶部 44 + 每行 ~96 + 底部 52，按库数量计算 |
| 上下限 | 夹取到 [220, 720]；超过上限时列表区滚动 |
| 触发 | 用"库数量"作内容指纹，变化时 `window.resize()`（同设置窗口的守卫思路） |
