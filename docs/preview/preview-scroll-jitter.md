# 预览区滚动抖动排查与修复

> 状态：**已实施；同步方式做成可切换，默认「比例跟随」**（2026-10-21 二次修订）· 待人工验收
> 范围：`ui/preview.rs`、`ui/editor.rs`、`core/config.rs`、`ui/settings.rs`
>
> 用户确认的现象与分诊：① 抖动出现在**滚编辑区时预览抖**；
> ② 关闭「同步滚动」后抖动消失 → 确认是同步写入；
> ③ 先选了**停止后对齐**（滚动中不写对端，绝对不抖）；
> ④ 后又要求"恢复旧版流畅观感" → 做成 `preview.sync_mode` 配置项；
> ⑤ 块锚点实测"又抖又不同步" → 默认改回**比例跟随** `ratio`，
>    块锚点保留为 `anchor` 档，仍可一键切回去对比。
> 相关：`docs/preview/scroll-sync-design.md`、`docs/editor/editor-scroll-wheel.md`
>
> ⚠️ **版本提示**：本文基于 `gpui-base 0.6.4` / `gpui-pre 0.3.5` 的源码事实。
> 升级到 0.8.0 / 0.3.9 后（2026-10-21），加上 0.8.0 在 macOS 默认启用
> scroll bounce，`set_scroll_offset` 的 deferred 语义与虚拟列表测量行为
> 需重新核对；同步参数可能需要重调。

### 0. 与"高亮版本"的关系（git 对比结论）

用户反馈"高亮功能那一版之后滚动同步变差"。对比 `a3eeaa6`（高亮前的版本）
与 `3499610`（`add hilight`）两个提交：

| 文件 | 高亮提交改了什么 | 是否涉及滚动同步 |
|------|-----------------|-----------------|
| `src/ui/editor.rs` | +`decorations` / `refresh_decorations`；Markdown 的 `set_highlighter` 由 `text` 改为 `markdown` | **否**，未触碰 `tick_scroll_sync` / `apply_*` / 任何滚动写入 |
| `src/ui/preview.rs` | 代码块配色换成 `highlight()` + `to_highlight_style` | **否** |
| `src/core/config.rs` | 高亮主题字段、旧 `code_theme` 迁移 | **否**，未改滚动/换行相关字段 |

补充验证：`gpui-base` 的 `drive_highlighter` 只在**文本编辑**时驱动
（`editor/mod.rs:149-161`），不在滚动路径上；`refresh_decorations` 只挂在
保存防抖里，也不在滚动路径上。**高亮本身不影响滚动。**

真正的差异在**工作区未提交的同步重构**：旧版（`a3eeaa6`）是"每帧按比例
（滚动百分比）双向推送"，新版是"按源码行锚点 + 方向锁 + 手势让位"。
锚点方案更准，但把"实时写对端"的代价暴露得更明显 → 观感变差。
所以修复不是回退重构，而是把**时机**做成可切换，默认取与旧版一致的实时跟随。

## 1. 根因（按对抖动的贡献排序）

### R0（**2026-10-21 定位：两端互推，能解释"停止后对齐也抖"**）

写入滚动位置是 **deferred** 的，落点还会被修正：

- 编辑区：`set_scroll_offset` 只种下一个 deferred offset，软换行下还要经过
  粗调 + 最多 3 次精调，落点与写入目标常差几像素甚至一整行；
- 预览：`scroll_to` 之后，虚拟列表会在布局阶段对未测量块 / `offset_in_item`
  做归一化（`rebase_pending_scroll`），落点同样会漂。

两端的"是否用户在滚"判定却是**纯像素比较**（`|off - last_scroll_y| > 0.5px`）：
于是**自己写进去的位置被自己当成用户手势** → 开 250ms 静默窗口 →
窗口结束后推回去 → 对端写入 → 对端也误判 → 再推回来 = **每 ~250ms 一次的互推**。
只要发生一次写入就能启动这个循环，所以"停止后对齐"（只写一次）同样会抖。

修复（两端对称）：
1. 手势判定前先做**回显过滤**：位置变了先算锚点，命中
   `SyncGuard::is_echo`（1.5 行 / 0.002）就不算用户手势；
2. `is_echo` 加 **500ms 时效**（`ECHO_TIMEOUT`），过期作废，
   避免用户之后自己滚到附近被误吸收；
3. 加**反推抑制**：刚被对端写过的一端，400ms（`PUSH_SUPPRESS`）内不反向推
   （用户在滚时不拦）。

### R-1（2026-10-21 三次修订）编辑区被拽回文章开头

表现：**一边打字，编辑区一边跳回开头**。三条触发链，全部来自"比例路径缺少
None 保护"：

1. 预览还没布局 / 内容不足一屏时 `content_size ≈ viewport`，
   `max = (content − viewport).max(1px) = 1px`，于是比例恒为 **0**
   （或恒为 1）→ 推给编辑区 → 编辑区被写到顶部（或底部）。
   行锚点时代有"未测量就不产生锚点"的保护，比例路径没有。
2. 输入防抖后预览重解析，虚拟列表把滚动位置打回顶部；这在预览侧看起来
   和"用户滚到了顶部"一模一样 → 照样推 0 → 编辑区跳回开头。
3. 编辑期间编辑区本该是权威端，却照单全收对端的滚动指令。

修复（三道闸，任一都能单独挡住）：
- `scroll_range()`：视口未布局 / 内容不足一屏 → 两端**读写都不做**
  （`editor.rs`、`preview.rs` 各一份，语义对称）；
- 预览侧 `CONTENT_SETTLE = 800ms`：内容刚变过就不推（覆盖"300ms 防抖 +
  重解析 + 重新测量"的完整往返）；
- 编辑区 `EDIT_PROTECT = 800ms`：最后一次输入后这段时间内不接受对端指令。

另外，"编辑之后"还有一类**不是同步**的跳顶：`save_now` / `refresh_doc` /
`refresh_decorations` / 外部变更 `set_value` 都可能让编辑控件重新布局并把
滚动位置清零。这些地方统一做了**前后比对 + 还原**（`schedule_save` 的防抖块、
`refresh_decorations`、`handle_external_change`）：不猜框架行为，
只在"确实被动过"时还原，同步块内也不会有用户滚动插进来。

排查这类问题靠落点日志：打开 `preview.debug_scroll_sync` 后，所有滚动写入
（`apply_ratio` / `apply_anchor` 粗调 / 精调 / `goto_line`）都会往 stderr 打
`[xink][scroll] 写入[xxx] 目标=… 当前=…`，还原与重载也会打点。

### R1（主因）未测量的块被当成"块内偏移 0" → 锚点整块跳

预览列表是虚拟列表，`ListState::bounds_for_item(ix)` 在两种情况下返回 `None`
（gpui-pre `elements/list.rs:711-729`）：

- `ix` 位于当前顶部块之前；
- 该 item **还没有被测量**。

原实现拿到 `None` 时用 `unwrap_or(px(0.))` 兜底，于是"块内比例"被当成 0
→ 锚点瞬间跳到**块的开头**。一个代码块可能有几十行，这个跳变远超回显容差，
两端互相纠正 —— **这就是"滚动时抖动非常严重"的直接来源**。

### R2 每帧写入滚动位置，与用户手势竞争

`scroll_to`/`set_offset` 是立即生效的（`list.rs:660-674`），所以同步每写一次，
预览就跳一次。用户滚轮期间被写 → 手感是"边滚边被拽"。

### R3 亚像素噪声被当成真实滚动

锚点换算经过"像素 → 块内比例 → 行号"的往返，有亚像素级抖动。原实现没有死区，
每个微小变化都会推给对端，对端再写回来 → 持续微调 = 视觉抖动。

### R4 `content_size` 在滚动过程中不断变化

虚拟列表边滚边测量新块，`content_size` 会持续变化。原实现用它做"内容变化 →
重新对齐"的判定，结果是**每帧都重新对齐 = 每帧写滚动** → 抖上加抖。

### R5 图片没有高度 → 加载完成后回流

预处理只写了 `style="width: N%"`（`core/markdown.rs:237`），而框架的 `<img>` 渲染
**只取 `width`、忽略 `height`**（`gpui-base text/node.rs:1814`），高度只能等图片
加载完才知道 → item 高度变化 → 位置漂移。

> 这一条**无法在应用层根除**：渲染代码在框架里，且不用 `height`。
> 只能靠"高度变化后重新对齐"（见修复第 4 条）把漂移纠正回来。
> 顺带说明：给 `<img>` 加 `width` 属性反而会覆盖 `style` 里的百分比宽度
> （`format/html.rs:190-207` 属性优先），所以**不能**靠它来规避。

## 2. 影响范围

- **开启「同步滚动」时**最明显（关闭后预览不再被写入，抖动消失——这也是分诊手段）。
- 长文档、含代码块 / 图片 / 表格的文档更明显（块高差异大，R1 的跳变更大）。
- 滚得快时更明显（未测量块更多）。
- 编辑区也会被带着抖（两端互相纠正）。

## 3. 修复内容

### 3.0 同步方式做成可切换：`preview.sync_mode`（**默认 `ratio`**）

（2026-10-21 二次修订：块锚点方案实测"又抖又不同步"，默认改回比例。）

| 取值 | 行为 | 适用 |
|------|------|------|
| `ratio`（**默认**） | 两端各按自己的滚动百分比对齐，滚动中持续跟随 | 连续平滑，与旧版观感一致 |
| `anchor` | 按 Markdown 顶层块对齐（源码行 → 块 → 像素） | 位置更准，但块边界处会跳 |
| `on_stop` | 滚动中**不读不写对端**，停下 250ms 后对齐一次 | 绝对不抖，滚动中对端不动 |

换成默认 `ratio` 的三条理由：

1. **换算连续**：比例是连续函数，滚动全程平滑；块锚点的"块内行比例 → 块内
   像素"是分段线性的，每跨一个块就跳一次，长代码块处尤其明显。
2. **读写对称**：两端各用自己的公式读写，读到的比例再写回去必然回到同一像素
   位置，回显天然落在容差内，不会互推（R0 的直接解药）。
3. **不依赖测量**：比例只看可滚动范围，不存在"未测量块"问题（R1 也一并消失）。

代价是"同一百分比在两端对应的内容不完全一致"（长代码块处会偏）。为把这个偏差
压到最小，**内容高度估算改用实测值**：软换行下"行数 × 行高"会系统性低估，
这里按 `px_per_source_line`（滚动中每 8 帧采样一次、指数平滑）估算
（`editor.rs::content_height`），`ratio_now` 与 `apply_ratio` 共用它。

> 顺带修掉一个会让同步几乎完全失效的 bug：死区 `DEAD_ZONE = 0.2` 的单位是
> **源码行**，直接套在比例锚点上等于 20% 的滚动范围 → 绝大多数推送被吃掉
> → "预览不跟着动"。现在按锚点种类分别取 0.2 行 / 0.002。

`on_stop` 下：本端滚动时只记 `pending_push = true`，等静默窗口结束
（250ms 无滚动）才读一次锚点、推一次、对端对齐一次。
理由：只要滚动中写对端，换算再准也会跳——块内渲染非线性、虚拟列表高度在变、
两端可滚动范围不同，写进去的位置与用户手上的位置永远差几像素到几十像素，
每帧写就是每帧跳。

连带收益（`on_stop`）：滚动中每帧只读一个 `scroll_offset()`，不再做 7 次布局探测，
也不再每 2 帧让对端重排 → 主线程负载大幅下降。

以下 1~6 是此前为"实时跟随"做的加固，策略改了之后仍保留（提高停止后那一次的精度）；
0 是 2026-10-21 补的（R0 互推，见 §1）：

0. **斩断互推**：手势判定前做回显过滤（`is_own_write`）、回显判定加 500ms 时效、
   刚被写过的一端 400ms 内不反推。

1. **拿不到块高度就不读写**（R1）
   - `current_anchor`：顶部块未测量 → 本帧**不产生锚点**（不再用 0 兜底）；
   - `apply_editor_anchor`：目标块未测量 → **不写**（不再把预览拽到块开头）。
2. **死区**（R3）：锚点变化 < 0.2 行不推送（`DEAD_ZONE`）。
3. **降频**（R2/R3）：推送改为每 2 帧一次；写入后跳过下一帧的读取，等布局稳定。
4. **重新对齐加冷却**（R4/R5）：块数变化或内容高度变化才对齐，且
   - 用户正在滚时不对齐；
   - 两次对齐间隔 ≥ 300ms（`REALIGN_COOLDOWN`）。
5. **手势让位**（R2）：`GestureGuard` 静默窗口内一律不写预览（上一轮已加，本轮复用）。
6. **探测减负**：编辑区软换行下的候选行 13 → 7，每帧少一半布局查询。

## 4. 验证方式

**自动化**：`cargo test` 全绿（323）。抖动本身是视觉现象，无单测覆盖，靠下面的清单。

**分诊（先做）**：设置 → 预览 → 关掉「同步滚动」
- 抖动消失 → 确认是同步写入导致，本次修复已覆盖；
- 仍然抖 → 是虚拟列表测量本身的问题（框架侧），请把现象（是否在特定文档/位置）告诉我。

**人工验收清单**（默认 `realtime`：滚动中对端持续跟随；若切 `on_stop`，
预期变为**滚动中对端不动，停下约 0.25 秒后对端跳到对应位置**）

- [ ] **滚编辑区：预览跟随滚动，不停在原地、不整块跳动（最核心的一条）**
- [ ] 滚预览：编辑区同样跟随，方向一致、不来回推
- [ ] 长文档（几百行 + 多个代码块）连续滚：被滚的一侧完全平稳，无上下跳/来回微调
- [ ] 快速甩动后松手：惯性衰减自然，松手瞬间不"弹一下"
- [ ] 滚过**图片**时：图片加载完成后位置不跳（允许一次性纠正，不应反复跳）
- [ ] 滚过**大表格 / 长代码块**的边界：不出现整块跳动
- [ ] 滚动条拖动：跟手，thumb 不跳
- [ ] 交替滚动（先滚编辑再滚预览）：只有一侧跟随，不来回推
- [ ] 对齐的位置准确（用 HUD 看 `Δ` 是否收敛到 1 行内）
- [ ] 仍有抖动 → 设置里把「同步时机」切成 `on_stop`，重跑前 4 条
- [ ] 切换标签 / 打开新笔记：预览会立刻对齐一次（不会停在上一篇的位置）
- [ ] 开着 HUD（`preview.debug_scroll_sync`）：停止滚动后 `Δ` 应收敛且稳定
- [ ] 关闭「同步滚动」后滚预览：完全平滑（作为基线对比）

## 5. 平台兼容性说明

- **桌面端**：本项目当前只构建 macOS（GPUI + Metal）。上述修复全部在
  应用层的滚动同步逻辑里（锚点换算 / 静默窗口 / 降频 / 死区 / 冷却），
  不依赖平台 API，Windows / Linux 构建同样适用（若将来支持）。
- **移动端**：当前**不支持**——无 iOS / Android 构建与打包，框架与事件模型
  （`ScrollWheelEvent` / 触控板惯性）也是桌面语义。滚动同步的这些约束
  （手势优先、写入冷却、未测量块不写）本身与输入设备无关，将来上移动端可直接沿用。
- 输入设备差异：触控板 = `Pixels` 增量 + 系统惯性；鼠标滚轮 = `Lines × 行高`。
  应用不自行加倍率，速度交给系统设置。

## 6. 遗留

- 图片高度回流（R5）只能在"高度变化后重新对齐"层面缓解，无法彻底消除；
  若框架将来在 `<img>` 渲染里使用 `height`，可在 `core/markdown.rs` 的预处理里
  补上真实尺寸（需要读图片头拿宽高），届时抖动会进一步减少。
- 虚拟列表"边滚边测量"固有的轻微高度修正（`measure_all` 已由框架开启），
  在超长文档首屏滚动时仍可能有一次性跳动。
