# 目录树交互增强（拖拽 / 导入 / 粘贴 / 刷新）— 评估与规划

> 状态：**P0 已实施**（2026-10-12）；其余待排期
> 已决策：排序（1b）**不做**；拖入支持整个目录；命名规则见 §8。
> 范围：`src/ui/file_tree.rs`、新增 `src/core/fs.rs`（文件操作服务）

---

## 1. 结论速览

| # | 需求 | 可行性 | 主要依据 | 优先级 |
|---|---|---|---|---|
| 4 | 刷新按钮 + 手动同步 | ✅ 高 | 复用现有扫描逻辑 | **P0** |
| 2 | 从访达拖入文件/图片 | ✅ 高 | `div::on_drop` + `ExternalDragPayload` | **P1** |
| 3 | 复制文件/图片后粘贴 | ✅ 高 | `ClipboardEntry::ExternalPaths` / `Image` | **P2** |
| 1a | 拖拽**移动**节点（改层级） | ⚠️ 中 | 拖拽 API 有，但树组件无内置支持，需自行实现 | **P3** |
| 1b | 拖拽**排序** | ❌ 低（需先解决顺序存储） | 文件系统没有"顺序"概念，必须引入额外元数据 | **单独立项** |

### 关键判断：需求 1 要拆成两件事

- **1a 移动（改层级）**：可行。拖 A 到目录 B → `fs::rename` → 重扫树。
- **1b 排序（调顺序）**：**不能靠文件系统实现**。目录树目前按名称排序，文件本身不记录顺序；
  要支持手动排序，必须额外存顺序（如每目录一个 `.xink-order.json`，或写进笔记 frontmatter），
  还要处理"新文件插入哪里、删除后重排、与外部改动冲突"。这是**独立的设计问题**，
  不建议混在拖拽里做。

## 3. 逐项方案

### 需求 4：刷新按钮（P0，约 0.5 天）

- 工具栏现有按钮（新建笔记 / 新建目录 / 重命名 / 移动 / 删除）旁新增「刷新」；
- 点击 → 重新扫描当前库目录 → 重建树 → `cx.notify()`；
- 复用现有的扫描函数，不新增扫描逻辑；
- 若项目已有文件系统监听（待确认，见 §6），刷新按钮定位为"手动兜底"，
  处理监听器漏事件（如休眠后、网络盘）的场景；
- 建议加 200ms 防抖，避免连点重复扫描。

### 需求 2：从访达拖入（P1，约 2–3 天）

- 树的每个**目录节点**挂 `on_drop`，整个树容器挂 `on_drop` 作为"落到根目录"的兜底；
- 拖入时给目标节点高亮（视觉反馈），`on_drag_move` 决定当前悬停目标；
- 落点解析出目标目录后，调用公共导入服务（§4）；
- 拖入的是目录时：递归复制整个目录（需确认是否允许，见 §6）。

### 需求 3：粘贴文件/图片（P2，约 2 天）

- 目录树（或当前选中目录）接受粘贴动作：`Cmd+V` / 右键菜单「粘贴」；
- 读 `cx.read_from_clipboard()`：
  - `ExternalPaths(paths)` → 复制这些文件到目标目录；
  - `Image(image)` → 生成文件名（如 `pasted-<时间戳>.png`）写入目标目录；
  - `String(text)` → **不**创建文件（避免误把一段文字变成笔记），仅当文本是单个路径时按路径处理；
- 与需求 2 共用同一个导入服务。

### 需求 1a：拖拽移动（P3，约 3–4 天）

- 源节点挂 `on_drag`（携带自己的路径），目标节点挂 `on_drop`；
- 校验规则（必须实现，否则会丢文件）：
  1. 不能把目录移动到**它自己或其子孙**里；
  2. 目标已存在同名文件 → 弹确认（覆盖 / 自动改名 / 取消），**不允许静默覆盖**；
  3. 跨磁盘/设备：`fs::rename` 会失败，需回退为"复制 + 删除源文件"，
     且删除前必须确认复制完整（大小一致）；
  4. 移动成功后再重扫树，避免树与实际不一致；
- 排序（1b）本期不做，树仍按名称排序。

## 4. 公共能力：抽一层文件服务

需求 2、3 都要"把一批外部文件放进某个目录"，应抽成纯函数便于单测：

```rust
// src/core/fs.rs
pub enum ImportMode { Copy, Move }

/// 把若干源文件导入目标目录；返回每个源的结果（成功路径 / 失败原因）
pub fn import_paths(paths: &[PathBuf], target_dir: &Path, mode: ImportMode)
    -> Vec<Result<PathBuf, ImportError>>;

/// 目标名冲突时生成不重名的新名字（a.png → a-1.png）
pub fn unique_name(dir: &Path, name: &str) -> PathBuf;

/// 安全移动：同设备用 rename，跨设备回退为 copy + 校验 + delete
pub fn move_path(from: &Path, to: &Path) -> Result<()>;
```

单测覆盖：重名改名、跨设备回退、移动到自身子目录被拒、导入失败不影响其他文件。

## 5. 风险与约束

| # | 风险 | 处置 |
|---|---|---|
| R1 | **数据丢失**（覆盖 / 跨设备移动中断） | 禁止静默覆盖；跨设备移动先复制再删除，且校验大小；失败保留源文件 |
| R2 | 大目录递归导入卡 UI | 放到后台任务（`cx.background_executor`），完成后再刷新树 |
| R3 | 外部改动冲突 | 导入/移动后强制重扫，以磁盘为准 |
| R4 | 权限（只读目录、沙盒） | 失败时给出可读提示，不 panic |
| R5 | 拖拽交互在不同平台表现差异 | macOS 优先验证，其他平台标注未验证 |
| R6 | 粘贴文本误建文件 | 仅路径文本才导入，普通文本忽略 |

非目标：不做撤销（Undo）、不做云同步冲突处理、不改动目录树的排序规则。

## 8. 待确认项的判断结果（2026-10-12）

### D1：外部拖入能否拿到文件路径 → **能**

`gpui-pre interactive.rs:694`：

```rust
pub struct ExternalPaths(pub SmallVec<[PathBuf; 2]>);
impl ExternalPaths { pub fn paths(&self) -> &[PathBuf] { &self.0 } }
```

拖入与剪贴板共用这一类型：拖入走 `div::on_drop`（`elements/div.rs:570`），
粘贴走 `ClipboardEntry::ExternalPaths`（`platform.rs:2569`）。
**结论：需求 2、3 都可行**，且可共用同一套"导入一批路径"的逻辑。

> 补充：`ExternalDragPayload`（`div.rs:649`）是**拖出**到系统用的，不是拖入。

### D2：是否已有文件监听 → **已有**

`src/core/watcher.rs` 提供 `VaultWatcher`，`FilesPanel` 持有
`watcher` / `watcher_task`（`file_tree.rs:37-38`），库加载时
`start_watcher`（`:379`）启动并自动同步外部改动。

**结论：刷新按钮是"兜底"**，用于监听可能漏掉的场景：休眠唤醒后、
网络盘/挂载盘、权限变化，或用户只是想马上确认一次目录状态。

### D3：拖入整个目录 → 支持（用户决策）

递归复制整个目录；实现时放到后台任务，避免大目录卡 UI。

### D4：导入文件的命名规则

| 规则 | 示例 |
|---|---|
| 保留原文件名，不做大小写/空格规范化 | `My Photo.png` 原样 |
| 冲突时在**主文件名**后加 `-N`（N 从 1 递增），扩展名不变 | `a.png` → `a-1.png` → `a-2.png` |
| 无扩展名同样处理 | `笔记` → `笔记-1` |
| 已带尾部序号则**先剥离再递增**，避免出现 `a-1-1.png` | `a-1.png` 再导入 → `a-2.png` |
| 同一批内多个同名文件依次递增，互不影响 | 两个 `a.png` → `a.png`、`a-1.png` |
| 目录同名适用同一规则 | `assets` → `assets-1` |
| 递增上限 999，超出返回错误而不是死循环 | — |

统一由 `core/fs.rs::unique_name(dir, name)` 实现，供导入（需求 2/3）
与移动（需求 1a 的冲突处理）共用。

## 10. 拖拽高亮反馈（2026-10-12）

### 10.1 框架能力边界（决定方案）

| 事件 | 是否提供 | 说明 |
|---|---|---|
| `on_drag`（发起） | ✅ `div.rs:621` | 携带自定义载荷，产生 `cx.active_drag` |
| `on_drag_move` | ✅ `div.rs:360` | **仅在存在 `active_drag` 时触发**（即内部拖拽才有） |
| `on_drop` | ✅ `div.rs:570` | 落点事件，外部拖入也可用 |
| `on_drag_enter` / `on_drag_leave` / 拖拽结束 | ❌ 无 | 无法直接感知"离开"与"取消" |

**关键结论**：从访达拖入属于**外部拖拽**，不进入 `active_drag`，因此
`on_drag_move` **不会触发**——外部拖入无法做"悬停高亮"。
高亮反馈的适用场景是**树内拖拽移动（需求 1a）**，故高亮与 1a 一并落地。

### 10.2 状态管理

- `FilesPanel.drag_hover: Option<PathBuf>` —— 当前悬停的**落点目录**；`None` 表示无高亮。
- 写入时机：仅 `on_drag_move` 命中节点时写入（内部拖拽）。
- 渲染时：节点路径与 `drag_hover` 相同 → 应用高亮样式。

### 10.3 触发与恢复

| 场景 | 处理 |
|---|---|
| 拖到**目录**上 | 高亮该目录（落点 = 自身） |
| 拖到**文件**上 | 高亮其所在目录（落点 = 父目录） |
| 拖到树的空白区 | 落点 = 库根（高亮根节点） |
| 松开（drop） | 执行移动后**立即清除** |
| 移出所有节点 | 由下一次 move 覆盖；若拖出窗口则依赖渲染兜底 |
| 拖拽取消 / 松手在空白处 | 无结束事件 → **渲染兜底**：每帧检查 `active_drag` 为空则清除 |

### 10.4 视觉与体验

- 视觉强度：用**主题 token** 的强调色作背景 + 同色系边框，不用刺眼色；
  与"选中态"区分（选中是实心强调色，拖拽高亮为浅底 + 边框）。
- 过渡：不做动画（框架未暴露过渡 API，硬做会闪烁）；靠即时切换保持响应。
- 防闪烁：只在落点**变化**时更新状态（相同则不动），避免每帧重绘。
- 防误触：`dragging` 载荷类型区分内外；外部拖入不写 `drag_hover`。

### 10.5 触控 / 移动端

本项目为 **macOS 桌面应用**（GPUI，非 WebView），当前不存在移动端/触控场景；
触控板的拖放仍走鼠标事件通道，行为一致。此项标记为 **N/A**（如未来支持触屏需重新评估）。

### 10.6 实施结果（需求 1a + 高亮，2026-10-12）

`src/ui/file_tree.rs`：

- 新增 `DragPreview` 视图：树内拖拽时跟随光标显示文件名（`on_drag` 的
  constructor 必须返回 `Entity<Render>`，这是框架要求）。
- `FilesPanel.drag_hover: Option<PathBuf>`：悬停落点，仅在**变化时**写入并 notify（防闪烁）。
- 节点：`on_drag`（发起，载荷 = 路径）、`on_drag_move`（更新落点）、
  `on_drop::<PathBuf>`（执行移动）、`on_drop::<ExternalPaths>`（导入，已有）。
  `on_drop` 按 `TypeId` push，因此同一元素可同时接收内外部两种载荷。
- 高亮样式：`accent` 浅底（18% 透明）+ 同色边框，与"选中态"（实心）区分。
- 移动规则：禁止移到自身/子目录；同名**自动改名**不覆盖；跨设备由
  `core::fs::move_path` 处理；移动后重扫树。
- 空白区域：`on_drag_move` 把落点设为库根，高亮随之切换。

**已知限制（框架所致）**：
`active_drag` 是 `pub(crate)`，外部无法查询，且框架没有 drag end / leave 事件。
因此"拖拽被取消（Esc / 拖出窗口）"无法感知，高亮会残留到下一次拖拽或鼠标移动；
已在代码中注明。拖到窗口内空白区已由容器级 `on_drag_move` 覆盖，不会误留。

验证：`cargo test` 135 passed、clippy 0 error、已 fmt。
