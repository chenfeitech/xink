> 结论：当前框架无法呈现文字底色，功能入口与代码全部移除。
> 本文保留作为调研记录，避免日后重复投入；详见 §11 与 §12。

## 1. 需求

在编辑器菜单中新增三项文字格式设置：① 选中文字背景色；② 文字颜色；③ 文字字体。
要求：集成到现有菜单、操作直观、设置后即时生效、并**保留在编辑内容中**。

## 2. 关键前提：先核实框架能力

"保留在编辑内容中"意味着要以某种**标记语法**写入 Markdown 源文件；而"立即看到效果"取决于
**预览渲染层能否解析该语法**。已对 `gpui-base-0.6.4` 的 HTML 渲染实现做核实：

**框架实际处理的 HTML 标签**（`text/format/html.rs`，全部 `local_name!` 取值）：

```
a b blockquote br code del em h1-h6 i img li mark ol s script strong style table u ul
```

- **无 `span`、无 `font`**；
- `font-family` / 前景色相关处理：**0 处**（`grep -c` 结果为 0）；
- 唯一与颜色相关的是 `<mark>`：`mark_color()`（`html.rs:109`）先读 `color` 属性、
  再读 `style` 的 `background-color`；`parse_mark_color()` 支持 `#hex` 与
  `black / white / blue / yellow` 四个命名色。

### 可行性结论

| # | 功能 | 可行性 | 依据 |
|---|---|---|---|
| 1 | **背景色** | ✅ **可行** | `<mark color="#facc15">文本</mark>`，预览可见 |
| 2 | 文字颜色（前景） | ❌ **不可行** | 框架无 `span`/`font`，无前景色解析；写入也渲染不出来 |
| 3 | 字体 | ❌ **不可行** | 框架无 `font-family` 处理 |

### 必须澄清的一点：编辑区无法显示颜色

编辑器是**源码模式**的纯文本编辑器（`EditorState`）。应用格式后，编辑区里看到的将是
标记本身（`<mark …>文字</mark>`），**不可能出现彩色文字**——要那样必须换成所见即所得内核，
而 Wysiwyg 已判定不在本期范围。

因此"实时预览、立即生效"在本期只能解释为：
**应用到选中文本后，右侧预览区在同一时间刷新并呈现效果**（编辑区只显示标记语法）。

## 3. 建议方案

### 3.1 采纳：背景色（功能 1）

| 项 | 做法 |
|---|---|
| 承载语法 | `<mark color="#RRGGBB">选中文字</mark>`（与 `mark_color` 的首选读取路径一致） |
| 无选中时 | 插入空标记并把光标放中间（沿用现有 `surround` 的行为，`editor.rs:961-968`） |
| 已有标记时 | 再次应用不同颜色 → 替换已有 `<mark>` 的 `color`（避免嵌套堆积） |
| 取消格式 | 提供"清除背景色"项，去掉 `<mark>` 外壳、保留文字 |
| 色板 | **预设色板**（8–10 个常用色）而非自由取色器：可控、无需新依赖、命名色有限也够用 |
| 生效 | 写入后走既有预览刷新链路（增量重解析），预览区即时呈现 |

### 3.2 不采纳：文字颜色与字体（功能 2、3）

写入 `<span style="color:…;font-family:…">` 可以做到"保留在内容中"（导出 HTML 时有效），
但**本应用预览里渲染不出来**——等于"设了看不见"，与项目"不留假功能"的原则冲突。

可选替代（需你决策，见 §6）：
- **A 什么都不做**：只交付背景色，等功能 2/3 有渲染能力后再加；
- **B 只写语法不渲染**：写入 `<span style>`，本应用预览不显示、导出 HTML 可见。**不推荐**；
- **C 自研渲染**：在 markdown 预处理阶段把自定义标记改写成框架能显示的节点。
  代价大且受限于框架没有正文字体/前景色接口，**不建议本期做**。

## 4. 交互设计

- 位置：现有工具栏（`editor.rs:467-543` 的 13 个按钮）末尾新增一个"背景色"按钮，
  与既有按钮同规格（`toolbar_button`：`small` + `ghost` + tooltip 说明功能）。
- 点击后弹出**色板**：优先用框架 `Popover`；若不便内嵌则退回下拉选择（实施时确认，见 §7）。
- 色板项：8–10 个预设色 + "清除背景色"。
- 键盘：不新增快捷键（现有 Format 快捷键由 `main.rs` 绑定，颜色为参数化操作不适用）。

## 5. 数据持久化

格式以**文本标记**写入笔记正文，因此天然随笔记保存，无需新增配置项或存储结构，
也不存在"设置丢失"问题；导出的 Markdown 交给支持 `<mark>` 的渲染器同样可见。

### 10.4 修复：设置后预览没反应（2026-10-10）

**现象**：选色后编辑区出现了 `<mark>` 标记，但预览区没有变化。

**根因**：预览刷新链路是 `InputEvent::Change` → `on_change` → `note.set_text`（version+1）
→ 防抖后 `refresh_doc`（版本守卫决定是否重算）。
而编辑控件的程序化修改（`state.replace` / `state.insert`）**不会发出 Change 事件**，
于是：

- `note` 的文本根本没同步（version 不变 → `refresh_doc` 直接返回，预览不重算）；
- 连带**自动保存也不会触发**——改动要等用户下一次输入才落盘。

**修复**：程序化修改后显式调用 `self.on_change(window, cx)`。
为此把应用/清除逻辑从自由函数改为 `EditorPanel` 的方法（需要访问 `note` 与保存调度），
色板回调改为经面板实体（`WeakEntity<EditorPanel>`）执行。

**顺带修复同类问题**：`apply_format`（加粗 / 斜体 / 列表等 13 个按钮）有完全相同的缺陷——
插入标记后预览要等下一次输入才刷新。已一并加上 `on_change` 调用。

> 经验：**任何用代码改编辑控件内容的地方，都要显式同步一次 `on_change`**，
> 不能假设 Change 事件会自己来。

### 10.5 图标调整（2026-10-10）

初版用 Lucide 的 `Highlighter`（纯细线条描边），在十几像素的工具栏尺寸下辨识度不足。
改为**自绘内联 SVG**：马克笔笔身用 `fill="currentColor"` 实心填充，底部高亮线
`stroke-width="3.5"` 加粗。与工具栏其他图标同为内联 SVG（`highlight_icon`），

## 11. 文字底色自研支持评估（2026-10-10）

### 11.1 决定性证据：框架只为"行内代码"绘制背景

`mark_highlight()`（`gpui-base text/node.rs:1683-1690`）：

```rust
if mark.code {
    highlight = highlight.highlight(node_cx.style.inline_code_highlight());
    font_family = Some(mono);                       // 等宽字体
}
if let Some(color) = mark.highlight {
    highlight.background_color = Some(color);       // ← 我们 <mark> 的颜色确实写进去了
}
InlineHighlight { style: highlight, font_size_scale: mark.code.then_some(0.875) }
```

而绘制端（`text/inline_flow.rs:398 / 404-435`）：

```rust
let is_code = highlights.iter().any(|(_, h)| h.font_size_scale.is_some());  // 只有 code 有
let background = if is_code {
    let color = highlights.iter().find_map(|(_, h)| h.style.background_color);
    for (_, h) in &mut highlights { h.style.background_color = None; }  // 取出来自己画矩形
    color.map(|c| (bounds, c))
} else {
    None                                            // ← 普通文本：不画背景
};
```

**结论**：`<mark>` 的 highlight **写入了** `style.background_color`，但框架**只在行内代码分支**把它画成背景矩形；普通文本的 run 背景不会被绘制。这与实测"文字正常、无底色"完全一致。

### 11.2 三条路径

| 路径 | 做法 | 视觉效果 | 成本 | 风险 |
|---|---|---|---|---|
| **A 曲线复用** | 预处理把高亮改写成 `<mark color><code>…</code></mark>`：code 触发绘制分支，mark 提供颜色 | 底色出现，但**字体变等宽、字号 ×0.875**（行内代码样式） | 低（改预处理 + 单测） | 视觉是"代码"而非"高亮"，可能不符预期 |
| **B 改框架** | fork / patch `inline_flow.rs`，让非 code 的 highlight 也绘制背景 | 正确的"高亮"外观 | 高 | 需维护框架分支，gpui-kit 升级时冲突 |
| **C 放弃** | 撤下按钮与色板 | — | 低 | 功能缺失（与文字色、字体同因） |

### 11.3 若要实施，需要支持的场景

1. 选中文字上色（含同一段落内的部分选中）
2. 已上色文字换色（替换颜色，不产生嵌套）
3. 清除底色（保留文字）
4. 空选区时插入标记并把光标放中间
5. 与既有行内语法共存：加粗、斜体、删除线、链接、行内代码（需定义嵌套与 merge 规则）
6. 明暗主题下均可读
7. 导出的 Markdown 在外部渲染器（支持 `<mark>`）中同样有效

### 11.4 期望的视觉表现

- 背景**贴合文字实际范围**；跨行时按行分段绘制，不越界
- **不改变字体族与字号**——这是路径 A 的最大偏差，也是判断它能否被接受的关键
- 与行高协调：不遮挡上下行文字
- 明暗主题下文字与底色对比度足够（不能出现"黄底白字看不清"）
- 与编辑器的选区高亮可区分（避免误认为被选中）

### 11.5 必须满足的约束

| # | 约束 |
|---|---|
| C1 | 颜色不硬编码，取值需与渲染能力匹配（当前只认 `#hex` 与四个命名色） |

| C5 | 持久化：标记随正文保存，不引入新的配置或存储结构 |
| C6 | 可回退：撤下功能后已写入的标记仍是合法 Markdown，不损坏笔记内容 |

### 11.7 决策与实施（2026-10-10）：采纳路径 A

**决策**：采纳 A——`<mark color="#hex"><code>文本</code></mark>`。
code 触发背景绘制分支，mark 提供颜色。**已接受的视觉偏差**：文字呈等宽字体、字号 ×0.875。

**实现**：`core/markdown.rs` 的 `mark_text` 生成双层包裹；`marked_inner` 同时识别
新旧两种写法（旧格式换色时自动升级为新格式，不会被二次包裹）。

**测试**（8 例）：包裹结构、换色不嵌套（mark 与 code 各只有一个）、换色不破坏内容、
清除保留文字、两种写法识别、嵌套/未闭合拒绝、旧格式升级。

**其余工作**：移除排查用的临时日志（保留面板释放的错误日志）；
`apply_highlight` / `clear_highlight` / `apply_format` 仍保留"on_change + 立即 refresh_doc"
的同步，确保选色后预览当下重算。

**验收重点**（人工）：预览区是否出现底色、底色是否用了所选颜色、
文字是否变为等宽小字（已知偏差）、清除与换色是否正常。

### 11.8 真正的根因：不是语法，是选色回调没执行（2026-10-10）

三次改语法（`<mark>` → 双层 `<mark><code>`）**全部无效**，因为编辑区压根没出现标记——
**选色回调从未被执行**。

- 原实现：工具栏按钮用 `Popover` + 自绘色块网格。Popover 在工具栏这种
  **每帧重建元素树**的场景下点击回调不稳定，表现为"点了没反应"。
- 改用 `DropdownButton` + `PopupMenuItem`：项目里已有两处成熟用法
  （`settings.rs:773`、`file_tree.rs:919`），且 `on_click` 提供 `&mut Window`，
  正好满足 `apply_highlight` 的需要。
- 菜单项支持 `icon`，用自绘色块 SVG（`swatch_icon`）保留"色板"的辨识度，
  代价是从"网格色板"变为"带色块的下拉菜单"。

> 教训：**先确认改动是否落地，再改渲染。**本次在语法上反复投入了三轮，
> 而真正的故障点在交互层——若一开始先看编辑区有无标记，可少走三次弯路。

## 12. 撤回记录（2026-10-10）

**决定**：撤回文字背景色功能（R2.7），与 R2.8（文字色）、R2.9（字体）同一原因——框架渲染能力不足。

### 12.1 移除范围

| 位置 | 移除内容 |
|---|---|
| `src/ui/editor.rs` | 工具栏入口、色板下拉菜单、`apply_highlight` / `clear_highlight`、`HIGHLIGHT_COLORS` 色板常量、`swatch_icon` / `highlight_icon`、相关导入 |
| `src/core/markdown.rs` | `mark_text` / `marked_inner` / `apply_mark_color` / `strip_mark` 及常量 |
| `src/core/markdown/tests.rs` | 8 个背景色用例 |
| `docs/REQUIREMENTS.md` | R2.7 标记为已撤回 |

测试回到 **122 passed**（撤回前 130，含 8 个背景色用例）。

### 12.2 为什么连路径 A 也不行

路径 A 借行内代码触发背景绘制（`<mark color><code>…</code></mark>`），理论上应生效，
但实测仍未呈现底色。可能原因（未再深挖，因投入已超出收益）：

- 嵌套标签的 `TextMark` 合并顺序导致 `highlight` 被 `code` 样式覆盖，或反之；
- inline HTML 产物未通过 `append_inline_html_blocks` 的白名单（非 Paragraph/Break 会被丢弃）。

### 12.3 已写入笔记的标记怎么办

测试期间若已写入 `<mark …><code>…</code></mark>`，**笔记内容不会丢失**：
预览会把它渲染为行内代码样式（等宽字、灰底），文字本身可读。
