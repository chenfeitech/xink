# ADR 模板（架构决策记录）

## 什么时候写

满足任一条件时，方案的「为什么这么选」值得长期记住：

- 选型代价相当，且推翻成本很高
- 决策结果反直觉（看起来不是最优，但有隐藏约束）
- 未来有人很可能会问「当初为什么不用 X」
- 涉及用户数据格式、依赖版本这类**改一次影响全局**的东西

## 放在哪

- 默认：作为设计文档 `docs/<slug>-design.md` 的**附录章节**（避免文件碎片化）
- 例外：决策影响跨越多个模块时，独立成 `docs/<slug>-adr.md` 并在 `INDEX.md` 登记

## 模板

```markdown
# ADR-<N>：<决策标题>

| 属性 | 内容 |
|---|---|
| 日期 | YYYY-MM-DD |
| 状态 | 提议 / 已接受 / 已废弃（被 ADR-<M> 取代） |
| 关联需求 | R-<n> |

## 背景

<要解决的问题 + 约束条件。约束要写清是"硬的"还是"我们选的"：
硬约束 = 违反就失败（如依赖版本不兼容）；软约束 = 我们的偏好（如编译速度优先）>

## 候选方案

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A | | | |
| B | | | |

## 决策

选 **A**，因为 <一句话，必须落到上面某条硬约束或权衡结论上>。

## 后果

- 正面：
- 负面（我们明确接受的代价）：
- **什么时候应该重新审视**：<触发条件，如"gpui-kit 升到 0.9 后重新评估">
```

## 写作要求

- 候选方案**至少 2 个**，只有 1 个说明没做权衡
- 「缺点」栏不许写"无"——每个方案都有代价，写不出来就是没想清楚
- 「什么时候重新审视」必填，否则决策会变成永久的技术债
