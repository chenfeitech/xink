# 方案设计

## 角色

基于已澄清的需求产出技术方案，说明权衡与被否决的理由。
**产出文档后停在 G2，等用户确认后才动 `src/`。**

- 流程位置：流水线阶段 2（`../../rules/00-pipeline.md` §3）
- 产物规范：`../../rules/08-artifacts.md` §3
- 门禁：`../../rules/07-quality-gates.md` G2
- 前置：需求文档已存在且 G1 通过

## 六步 SOP

### Step 1 底盘核查

先加载技术铁律，确认方案不触碰：

| 规则 | 核查点 |
|---|---|
| `../../rules/01-gpui-stack.md` | 是否引入新依赖 / 改 `Cargo.toml`？版本会不会多出一份？（`cargo tree -d`） |
| `../../rules/02-architecture.md` | 逻辑放哪一层？`core/` 里的逻辑能否不建窗口就跑通测试？ |
| `../../rules/04-notes-domain.md` | 是否涉及磁盘真值、原子写盘、外部变更、索引可重建？ |

### Step 2 框架能力核实

涉及 GPUI 组件能力时，**先查 <https://gpui-kit.com> 或依赖源码**，不凭记忆判断。

> 历史教训（`../../rules/05-design-first.md` §4）：曾误判「框架没有链接点击回调」
> 「没有缩进设置」，源码核实后都是错的；也误判过「拼写检查不支持」（这条是对的）。
> **先查证再下结论，比事后返工便宜得多。**

### Step 3 生成 ≥2 个方案

对比维度固定四项：改动面 / 可测性 / 对用户数据的风险 / 后续扩展性。

**禁止只给一个方案**——只有一个方案无法判断权衡是否充分，G2 直接不通过。

### Step 4 权衡表

写明"选了 A 就放弃了什么"，被否决方案**必须附否决理由**。

### Step 5 数据模型与迁移

- 持久化格式（文件路径、JSON 字段）
- 旧数据兼容与迁移路径
- 派生数据是否可重建（`../../rules/04-notes-domain.md` §1：索引随时可删可重建）

### Step 6 人工验收清单

只能靠人眼验的（滚动手感、着色配色、气泡位置、性能体感）单独列出，
登记到 `../../../docs/ACCEPTANCE.md`，**不要**留在设计文档里
（规则见 `../../rules/10-acceptance.md`）。

## 十章模板

见 `../../rules/05-design-first.md` §2：现状与问题 / 目标·非目标 / 方案概述 /
数据模型与持久化 / 交互流程 / 异常与边界 / 测试计划 / 人工验收清单 / 风险与开放问题 / 实施步骤。

## 强约束

| 编号 | 约束 |
|---|---|
| C-1 | **不改动 `src/`**；G2 未过（用户未确认）不得动生产代码 |
| C-2 | 现状章节每条结论附 `文件:行号` 证据，禁止"应该是" |
| C-3 | 被否决方案 ≥1 个且附理由 |
| C-4 | 需用户拍板的开放问题**单独列出**，不得自行决定 |
| C-5 | 不捏造 API / 字段；不确定写 `> 待补充` |
| C-6 | 测试计划必须区分「能自动化」与「要人工」 |
