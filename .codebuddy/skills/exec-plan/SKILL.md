# 研发计划拆解

## 角色

把确认后的设计拆成**可独立验证、可排序**的任务序列。**不改代码。**

- 前置：设计文档已存在且 G2 通过（用户确认）
- 产物：`docs/exec-plans/<slug>.md`（模板见 `../../../docs/exec-plans/README.md`）
- 规范：`../../rules/08-artifacts.md` §4
- 门禁：`../../rules/07-quality-gates.md` G3

## 五步 SOP

### Step 1 分期

按设计文档 §10「实施步骤」的 M1 / M2 / … 分期。
**每期产物必须可独立验证**——这是分期唯一的判据。

### Step 2 拆任务

粒度判据，满足任一即可停止再拆：

- 一次提交能装下
- 改完能**独立编译通过**
- 验收命令能跑出明确结果

反例：「实现整个搜索功能」太大；「改个变量名」太小，合并进相邻任务。

### Step 3 依赖排序

标出前置依赖形成 DAG，无依赖的标「可并行」。
**禁止出现"全做完才能编译"的任务**——那说明拆得不对。

### Step 4 定优先级与档位

| 项 | 取值 |
|---|---|
| 优先级 | P0（不做则功能不成立）/ P1（体验）/ P2（锦上添花） |
| 档位 | S（单文件小改）/ M（新建文件 + 参考材料）/ L（跨多文件 + 需演练） |

**不用人天估算** —— AI 估人天没有意义，改用「改动面 + 是否新建模块 + 是否需人工验收」。

### Step 5 每任务写清八项

`T-n` / 内容 / 依赖 / 优先级 / 涉及文件 / 验收方式 / 关联 `R-n` / 状态。

「验收方式」必须可执行：要么是命令，要么写明人工验什么。写"完成即可"视为未拆到位。

## 关键路径

在计划文件里标出最长依赖链，让用户知道哪里会卡、哪几项能并行。

## 交付

计划写完后交给用户过一遍——**任务拆解是最后一道低成本纠偏点**，
设计错了改设计，计划错了改计划，都比实施到一半返工便宜。

## 强约束

| 编号 | 约束 |
|---|---|
| C-1 | **不改动 `src/`** |
| C-2 | 每个任务必须有验收方式（命令或人工） |
| C-3 | 不存在"全做完才能编译"的任务 |
| C-4 | 每个 P0 任务关联 ≥1 条 `R-n` |
| C-5 | 不捏造；不确定写 `> 待补充` |
| C-6 | 涉及文件列要写具体路径，不写"相关模块" |
