# 需求理解与澄清

## 角色

把一句高层或模糊的需求，变成带编号、含非目标与边界条件的需求规格。
**本技能不写代码、不改 `src/`。** 产出文档后停在 G1，等用户确认方向再进 `solution-design`。

- 流程位置：流水线阶段 1（`../../rules/00-pipeline.md` §3）
- 产物规范：`../../rules/08-artifacts.md` §2
- 门禁：`../../rules/07-quality-gates.md` G1
- 缺陷修复且满足 `../../rules/00-pipeline.md` §4 三条豁免 → **跳过本技能**，直达实施

## 四步 SOP

### Step 1 归类

判断属于哪一类，决定后续路径：

| 类别 | 路径 |
|---|---|
| 新增功能 / 中等以上改动 | 走完整 G1 → G2 |
| 缺陷（现象明确、改法唯一、≤1 模块） | 跳 G1/G2，直达实施 + 事后补三行说明 |
| 重构 / 性能优化且行为不变 | 免需求文档，可免设计文档（`../../rules/05-design-first.md` §3） |
| 调研 / 评估 | 只产出 `docs/<slug>-eval.md`，不进 G2 |

### Step 2 查证现状（禁止"应该是"）

用 `search_content` / `read_file` 找到相关代码，**每条结论附 `文件:行号` 证据**。

- 查不到就写"未找到相关实现"，**不要推测**
- 涉及框架能力（GPUI 组件是否支持某特性）时**先查文档或源码**，不凭记忆判断
- 这一步做不实，后面全错——历史教训见 `../../rules/05-design-first.md` §4

### Step 3 生成假设清单

对模糊点生成 3~7 条假设，每条三列：

| # | 假设点 | 候选取值 | 不确认时的默认 |
|---|---|---|---|
| A1 | 触发时机 | 点击时 / 选中时 / 悬停时 | 点击时 |
| A2 | 作用范围 | 当前库 / 全部库 | 当前库 |

**默认值必须是可逆的、代价最小的那个**，并在清单里写明。

### Step 4 结构化提问

- **一次性**把问题打包成表格交给用户，**不要挤牙膏式追问**
- **不问开放式问题**（"你想怎么做？"），只给选项 + AI 的默认建议
- 用户可回"都按默认"一次性采纳
- **必须问**：无法从代码推断的产品偏好（交互形态、默认行为、优先级）
- **不要问**：能从代码或现有设计文档推断的技术事实

## 边界条件

逐条过 `references/boundary-checklist.md` 的九项，标注「适用 / 不适用 / 要人工验」。
适用项必须在需求文档 §4「边界与约束」写明处理方式。

## 产出

`docs/<slug>-requirements.md`，五个必备章节见 `../../rules/08-artifacts.md` §2。
写完对照 G1 逐条自检，机器项自判通过、"待用户拍板"清单清空后交付用户。

## 强约束

| 编号 | 约束 |
|---|---|
| C-1 | **不改动** `src/` 下任何生产代码 |
| C-2 | **不捏造** API / 字段 / 数据 / 结论；不确定写 `> 待补充` |
| C-3 | 现状描述**必须**附 `文件:行号` 证据 |
| C-4 | 「待用户拍板」清单未清空前，G1 不得判通过 |
| C-5 | 非目标章节**不得为空** |
| C-6 | 不代替用户做产品偏好决策；选型代价相当时必须交回 |
