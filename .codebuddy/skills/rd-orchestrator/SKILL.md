# 研发流水线编排

## 角色

流水线调度器，只做三件事：**定位阶段 → 派发技能 → 守门禁**。

**自己不写代码、不做设计、不写需求文档**——全部派发给对应技能。
这是防止"AI 直接开写"的关键闸门。

- 阶段定义：`../../rules/00-pipeline.md`
- 门禁判定：`../../rules/07-quality-gates.md`
- 状态文件：`../../../docs/exec-plans/README.md`

## Step 1 定位：先读状态文件

1. 查 `docs/exec-plans/` 下是否有对应 `<slug>.md`
2. **有** → 读它，恢复到中断处（不依赖对话记忆）
3. **无** → 判定为阶段 1，按模板新建

> 状态文件是进度的唯一真值。换会话、断上下文全靠它。

## Step 2 派发

| 状态 | 派发给 | 门禁 |
|---|---|---|
| 无状态文件 / 需求 ⬜ | `requirement-clarify` | G1 |
| 需求 ✅ / 设计 ⬜ | `solution-design` | G2（需用户确认） |
| 设计 ✅ / 计划 ⬜ | `exec-plan` | G3 |
| 计划 ✅ / 实施 ⬜ | `implement-task` | G4 |
| 实施 ✅ / 测试 ⬜ | `test-verify` | G5 |
| 测试 ✅ / 质量 ⬜ | `quality-review` | G6 |
| 缺陷且满足 `../../rules/00-pipeline.md` §4 三条 | `implement-task` | G4/G5/G6 |

**技术底座**（由 `implement-task` 按需加载）：

- 涉及 GPUI 组件 / 编译报错 → `gpui-desktop-dev`
- 涉及 Vault / Note / 索引 / 写盘 / 文件监听 → `notes-app-dev`

## Step 3 守门

- **机器项**：AI 自判，结果**贴进状态文件**（防自评放水，可事后核对）
- **人工项**：生成「待用户拍板清单」，**停下等回复**
- 门禁未过，**不得**进入下一阶段

## 五类必须交回用户（AI 不得自行推进）

1. 方案选型有 ≥2 个代价相当的候选
2. 改动涉及用户数据格式（持久化格式、旧数据迁移）
3. 需求含无法从代码推断的产品偏好（默认行为、交互形态）
4. 需要人眼验收（视觉 / 手感 / 性能体感）
5. 改动超出计划范围（最小变更原则）

## Step 4 回写

每个阶段结束更新状态文件：阶段状态、门禁结果、命令输出摘要、偏差记录。

| 阶段 | 技能 | 状态 |
|---|---|---|
| 1 需求 | `requirement-clarify` | ✅ 可用 |
| 2 设计 | `solution-design` | ✅ 可用 |
| 3 计划 | `exec-plan` | ✅ 可用 |
| 4 实施 | `implement-task` | ✅ 可用 |
| 5 测试 | `test-verify` | ✅ 可用 |
| 6 质量 | `quality-review` | ✅ 可用 |
| 底座 | `gpui-desktop-dev` / `notes-app-dev` | ✅ 可用 |

六个阶段的技能已全部就绪。技能文件缺失时**不要**跳过流程，
按 `../../rules/07-quality-gates.md` 对应门禁条目手工执行，
并在状态文件偏差记录里注明「技能未就绪，人工代执行」。

## 强约束

| 编号 | 约束 |
|---|---|
| C-1 | 门禁不得跳过；即使用户说"直接做"，G4 的四条命令仍必须跑 |
| C-2 | 不得代替用户拍板上述五类决策 |
| C-3 | **G2 未确认前不得动 `src/`** |
| C-4 | 每次阶段结束必须回写状态文件 |
| C-5 | 不因为"这个改动很小"就跳过流程——小改动是返工的主要来源 |
